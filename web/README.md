# web — интерфейс канбан-доски

Фронтенд спринта 1: четыре колонки, drag&drop, карточки с приоритетом, комментарии.
Работает по [контракту API](../docs/api-contract.md).

**Стек: vanilla JS (ES-модули) + нативный HTML5 drag&drop, без сборки.**
Доска на 4 колонки и 7 эндпоинтов не окупает тулчейн: нет `node_modules`, нет шага
сборки, страница открывается сразу — и это же упрощает интеграцию лиду.

## Запуск

Сначала бэкенд:

```bash
cd server && pip install -r requirements.txt && python run.py   # :8000
```

Затем доска:

```bash
cd web && python3 serve.py        # http://localhost:5173
```

`serve.py` отдаёт статику и проксирует `/api/*` на бэкенд, поэтому страница и API
живут на одном origin. Так доска работает и на удалённом стенде, где браузеру
пользователя недоступен `localhost:8000`.

| Переменная | По умолчанию | Зачем |
|---|---|---|
| `KANBAN_API` | `http://localhost:8000` | адрес бэкенда для прокси |
| `PORT` / `--port` | `5173` | порт доски |

Сборки нет — правки видны после обновления страницы (`Cache-Control: no-store`).

### Без прокси

`index.html` можно открыть файлом (`file://`) — тогда запросы идут прямо на
`http://localhost:8000/api/v1` (CORS на бэкенде открыт). Другой адрес API
задаётся параметром в URL, без правки кода:

```
http://localhost:5173/?api=http://192.168.1.10:8000/api/v1
```

## Тесты

```bash
pip install playwright pytest && python -m playwright install chromium
cd web && python -m pytest tests/ -q      # 10 тестов
```

Нужны поднятые сервер и доска. Тесты меняют данные — гоняйте на отдельной базе:
`KANBAN_DB=/tmp/ui.db python run.py`.

Покрыто: рендер колонок, счётчики, создание карточки, блокировка пустого заголовка,
drag&drop с проверкой сохранения на сервере, откат при отказе API, комментарии,
редактирование, отсутствие ошибок в консоли.

## Структура

```
web/
├── index.html          # разметка и стили
├── api.js              # адаптер API — единственное место с fetch
├── app.js              # состояние, рендер, drag&drop, диалоги
├── serve.py            # дев-сервер: статика + прокси на API
└── tests/test_board.py # UI-тесты (Playwright)
```

**Адаптер изолирован**: `app.js` не знает про HTTP, пути и коды — только вызывает
`api.listCards()`, `api.moveCard()` и т.д. Переезд на другой транспорт или моки —
правка одного файла.

## Как это работает

- **Drag&drop** — нативный HTML5. Колонка подсвечивается при наведении, перенос
  вызывает `PATCH /cards/{id}` со сменой статуса.
- **Оптимистичный UI**: карточка переезжает сразу, не дожидаясь сервера. Если
  запрос упал — карточка **возвращается назад** и появляется уведомление. Доска
  не должна показывать состояние, которого нет на сервере.
- **Ошибки видны**: любая неудача API даёт всплывающее сообщение с кодом и текстом
  (`Не удалось перенести карточку #3 — ошибка 422`). Ошибки не исчезают
  автоматически, успехи гаснут через 3.5 секунды.
- **Валидация на клиенте** дублирует контракт (непустой заголовок ≤ 200 символов),
  чтобы не гонять заведомо плохой запрос, но последнее слово за сервером: `422`
  показывается прямо в форме.
- **Счётчики комментариев** подгружаются фоново и не блокируют отрисовку доски;
  их сбой не тревожит пользователя — это украшение, а не данные.

## Расхождение с контрактом (для QA и лида)

Контракт обещает `422 {"detail": "..."}` **строкой**, но во влитом бэкенде нет
обработчика `RequestValidationError`, поэтому FastAPI отдаёт `detail` **массивом
объектов**:

```json
{"detail": [{"type": "value_error", "loc": ["body", "title"], "msg": "..."}]}
```

Адаптер поддерживает оба формата и в любом случае показывает человеку внятный текст.
Но формально это баг бэкенда либо неточность контракта — решение за лидом.

Второй момент: `GET /cards?status=` с пустым значением у текущего бэкенда даёт `422`.
Фронт пустой фильтр просто не отправляет, так что на интерфейсе это не сказывается.

## Не в этой фазе

Авторизация, websocket, поиск, сортировка внутри колонки, мобильный drag&drop
(на тач-устройствах перенос доступен через диалог: карточка → «Редактировать» →
статус) — кандидаты в спринт 2.
