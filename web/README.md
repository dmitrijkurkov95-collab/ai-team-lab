# web — интерфейс канбан-доски

Фронтенд спринта 1: четыре колонки, drag&drop, карточки с приоритетом, комментарии.
Работает по [контракту API](../docs/api-contract.md).

**Стек: vanilla JS (ES-модули) + нативный HTML5 drag&drop, без сборки.**
Доска на 4 колонки и 7 эндпоинтов не окупает тулчейн: нет `node_modules`, нет шага
сборки, страница открывается сразу — и это же упрощает интеграцию лиду.

## Запуск

Сначала бэкенд:

```bash
cd server && pip install -r requirements.txt && python run.py   # :8000
```

Затем доска:

```bash
cd web && python3 serve.py        # http://localhost:5173
```

`serve.py` отдаёт статику и проксирует `/api/*` на бэкенд, поэтому страница и API
живут на одном origin. Так доска работает и на удалённом стенде, где браузеру
пользователя недоступен `localhost:8000`.

| Переменная | По умолчанию | Зачем |
|---|---|---|
| `KANBAN_API` | `http://localhost:8000` | адрес бэкенда для прокси |
| `PORT` / `--port` | `5173` | порт доски |

Сборки нет — правки видны после обновления страницы (`Cache-Control: no-store`).

### Без прокси

`index.html` можно открыть файлом (`file://`) — тогда запросы идут прямо на
`http://localhost:8000/api/v1` (CORS на бэкенде открыт). Другой адрес API
задаётся параметром в URL, без правки кода:

```
http://localhost:5173/?api=http://192.168.1.10:8000/api/v1
```

## Тесты

```bash
pip install playwright pytest && python -m playwright install chromium
cd web && python -m pytest tests/ -q      # 17 тестов
```

Нужны поднятые сервер и доска. Тесты меняют данные — гоняйте на отдельной базе:
`KANBAN_DB=/tmp/ui.db python run.py`.

Покрыто: рендер колонок, счётчики, создание карточки, блокировка пустого
заголовка, drag&drop с проверкой сохранения на сервере, накопление правок при
обрыве сети и их отправка после восстановления, схлопывание повторных
перемещений, откат при `4xx`, информативность подтверждения удаления,
комментарии, редактирование, отсутствие ошибок в консоли.

Тесты убирают за собой: созданные карточки удаляются, изменённые заголовки
возвращаются. Прогон не оставляет мусора на общей доске.

## Структура

```
web/
├── index.html          # разметка и стили
├── api.js              # адаптер API — единственное место с fetch
├── sync.js             # очередь отложенных операций и автоповтор
├── app.js              # состояние, рендер, drag&drop, диалоги
├── serve.py            # дев-сервер: статика + прокси на API
└── tests/test_board.py # UI-тесты (Playwright)
```

**Адаптер изолирован**: `app.js` не знает про HTTP, пути и коды — только вызывает
`api.listCards()`, `api.moveCard()` и т.д. Переезд на другой транспорт или моки —
правка одного файла.

## Поведение при недоступном API

Доска не «умирает» вместе с бэкендом. Решение о том, копить правку или
откатывать, принимается **по идемпотентности операции** — это единственный
честный критерий, по которому можно решать за пользователя:

| Ситуация | Что происходит |
|---|---|
| Сеть/сервер недоступны (`нет ответа`, `5xx`), перемещение карточки | Карточка **остаётся** в новой колонке, правка копится в очереди и повторяется автоматически с нарастающей паузой (1с → 2с → 5с → 10с → 15с) |
| Сервер ответил `4xx` (например, `422`) | Повтор бессмыслен — карточка **откатывается**, показывается ошибка с текстом от сервера |
| Создание/удаление при сбое | **Не** повторяются автоматически: неизвестно, применился ли запрос, и повтор `POST` рискует создать дубль. Пользователь видит ошибку и решает сам |

**Индикатор синхронизации** в шапке показывает состояние: «всё сохранено» /
«синхронизация…» / «N правок ждут сети» с кнопкой «Повторить». Он информирует,
но не блокирует работу — доской можно продолжать пользоваться.

Дополнительно:

- **Схлопывание**: несколько перемещений одной карточки заменяют друг друга —
  важен только последний статус. Иначе после долгого офлайна доска отыграла бы
  всю историю перетаскиваний.
- **Возврат сети** (событие `online`) запускает отправку немедленно, не дожидаясь
  очередной паузы.
- **Обновление** при непустой очереди сначала отправляет накопленное: иначе
  ответ сервера затёр бы неотправленные правки.
- **Уход со страницы** с неотправленными правками вызывает предупреждение
  браузера — очередь живёт в памяти и перезагрузку не переживает.

Очередь сознательно **не** сохраняется в `localStorage`: восстановленная правка
может относиться к карточке, удалённой с другого клиента, и требует инвалидации.
Это отдельная задача, а не часть устойчивости к сбоям сети.

## Как это работает

- **Drag&drop** — нативный HTML5. Колонка подсвечивается при наведении, перенос
  вызывает `PATCH /cards/{id}` со сменой статуса.
- **Оптимистичный UI**: карточка переезжает сразу, не дожидаясь сервера, —
  дальше по таблице выше.
- **Подтверждение удаления** информативное: если у карточки есть комментарии,
  в предупреждении названо их количество и сказано, что это необратимо. Пустую
  карточку такой текст не сопровождает — рефлекторное «вы уверены?» на всё
  подряд приучает жать «да» не глядя.
- **Ошибки видны**: любая неудача API даёт всплывающее сообщение с кодом и текстом
  (`Не удалось перенести карточку #3 — ошибка 422`). Ошибки не исчезают
  автоматически, успехи гаснут через 3.5 секунды.
- **Валидация на клиенте** дублирует контракт (непустой заголовок ≤ 200 символов),
  чтобы не гонять заведомо плохой запрос, но последнее слово за сервером: `422`
  показывается прямо в форме.
- **Счётчики комментариев** подгружаются фоново и не блокируют отрисовку доски;
  их сбой не тревожит пользователя — это украшение, а не данные.

## Формат ошибок

Расхождение по `422`, найденное при интеграции, **закрыто** (PR #8): бэкенд отдаёт
`detail` строкой, подробности — в необязательном поле `errors`. Формат зафиксирован
в контракте.

Адаптер всё равно поддерживает **оба** формата (строку и массив объектов Pydantic):
это дешёвая страховка на случай, если рядом окажется сервер другой версии.

Мелочь на заметку: `GET /cards?status=` с пустым значением даёт `422` — enum не
принимает пустую строку. Фронт пустой фильтр просто не отправляет, на интерфейсе
это не сказывается.

## Не в этой фазе

Авторизация, websocket, поиск, сортировка внутри колонки, мобильный drag&drop
(на тач-устройствах перенос доступен через диалог: карточка → «Редактировать» →
статус) — кандидаты в спринт 2.
