# web — интерфейс канбан-доски

Фронтенд спринта 1: четыре колонки, drag&drop, карточки с приоритетом, комментарии.
Работает по [контракту API](../docs/api-contract.md).

**Стек: vanilla JS (ES-модули) + нативный HTML5 drag&drop, без сборки.**
Доска на 4 колонки и 7 эндпоинтов не окупает тулчейн: нет `node_modules`, нет шага
сборки, страница открывается сразу — и это же упрощает интеграцию лиду.

## Запуск

Сначала бэкенд:

```bash
cd server && pip install -r requirements.txt && python run.py   # :8000
```

Затем доска:

```bash
cd web && python3 serve.py        # http://localhost:5173
```

`serve.py` отдаёт статику и проксирует `/api/*` на бэкенд, поэтому страница и API
живут на одном origin. Так доска работает и на удалённом стенде, где браузеру
пользователя недоступен `localhost:8000`.

| Переменная | По умолчанию | Зачем |
|---|---|---|
| `KANBAN_API` | `http://localhost:8000` | адрес бэкенда для прокси |
| `PORT` / `--port` | `5173` | порт доски |

Сборки нет — правки видны после обновления страницы (`Cache-Control: no-store`).

### Без прокси

`index.html` можно открыть файлом (`file://`) — тогда запросы идут прямо на
`http://localhost:8000/api/v1` (CORS на бэкенде открыт). Другой адрес API
задаётся параметром в URL, без правки кода:

```
http://localhost:5173/?api=http://192.168.1.10:8000/api/v1
```

## Тесты

```bash
pip install playwright pytest && python -m playwright install chromium
cd web && python -m pytest tests/ -q      # 20 тестов
```

Нужны поднятые сервер и доска. Тесты меняют данные — гоняйте на отдельной базе:
`KANBAN_DB=/tmp/ui.db python run.py`.

Покрыто: рендер колонок, счётчики, создание карточки, блокировка пустого
заголовка, drag&drop с проверкой сохранения на сервере, накопление правок при
обрыве сети и их отправка после восстановления, схлопывание повторных
перемещений, откат при `4xx`, информативность подтверждения удаления,
комментарии, редактирование, отсутствие ошибок в консоли.

Тесты убирают за собой: созданные карточки удаляются, изменённые заголовки
возвращаются. Прогон не оставляет мусора на общей доске.

## Структура

```
web/
├── index.html          # разметка и стили
├── api.js              # адаптер API — единственное место с fetch
├── sync.js             # очередь отложенных операций, автоповтор, исходы конфликтов
├── poll.js             # фоновый опрос доски: интервал, backoff, свежесть
├── app.js              # состояние, рендер, drag&drop, диалоги
├── serve.py            # дев-сервер: статика + прокси на API
└── tests/test_board.py # UI-тесты (Playwright)
```

**Адаптер изолирован**: `app.js` не знает про HTTP, пути и коды — только вызывает
`api.listCards()`, `api.moveCard()` и т.д. Переезд на другой транспорт или моки —
правка одного файла.

## Поведение при недоступном API

Доска не «умирает» вместе с бэкендом. Решение о том, копить правку или
откатывать, принимается **по идемпотентности операции** — это единственный
честный критерий, по которому можно решать за пользователя:

| Ситуация | Что происходит |
|---|---|
| Сеть/сервер недоступны (`нет ответа`, `5xx`), перемещение карточки | Карточка **остаётся** в новой колонке, правка копится в очереди и повторяется автоматически с нарастающей паузой (1с → 2с → 5с → 10с → 15с) |
| Сервер ответил `4xx` (например, `422`) | Повтор бессмыслен — карточка **откатывается**, показывается ошибка с текстом от сервера |
| Карточку удалили с другого клиента (`404`) | Правка инвалидируется, карточка убирается с доски — см. «Конфликты с чужими правками» |
| Создание/удаление при сбое | **Не** повторяются автоматически: неизвестно, применился ли запрос, и повтор `POST` рискует создать дубль. Пользователь видит ошибку и решает сам |

**Индикатор синхронизации** в шапке показывает состояние: «всё сохранено» /
«синхронизация…» / «N правок ждут сети» с кнопкой «Повторить». Он информирует,
но не блокирует работу — доской можно продолжать пользоваться.

**Сверка полноты данных.** Ответ `GET /cards` содержит заголовок `X-Total-Count`
— сколько карточек попадает под фильтр. Доска сравнивает его с длиной полученного
списка: при расхождении показывается предупреждение. Это ловит случай, когда
сервер ответил `200`, но выдача неполная (issue #21: при гонке в БД часть записей
терялась) — ошибки нет, показывать нечего, и без сверки доска молча нарисовала бы
неполную картину.

Сверка действует, только пока доска запрашивает список **без `limit`**
(константа `LOAD_LIMIT` в `app.js`). По контракту `X-Total-Count` не учитывает
лимит, поэтому при постраничной загрузке расхождение станет штатным — условие
отключает проверку автоматически, а не даёт ей начать врать.

Дополнительно:

- **Схлопывание**: несколько перемещений одной карточки заменяют друг друга —
  важен только последний статус. Иначе после долгого офлайна доска отыграла бы
  всю историю перетаскиваний.
- **Возврат сети** (событие `online`) запускает отправку немедленно, не дожидаясь
  очередной паузы.
- **Обновление** при непустой очереди сначала отправляет накопленное: иначе
  ответ сервера затёр бы неотправленные правки.
- **Уход со страницы** с неотправленными правками вызывает предупреждение
  браузера — очередь живёт в памяти и перезагрузку не переживает.

Очередь сознательно **не** сохраняется в `localStorage`. Инвалидация правок уже
реализована (см. ниже), но переживание перезагрузки требует ещё и разрешения
расхождений накопленного состояния с серверным — это отдельная задача.

## Конфликты с чужими правками

Доска многопользовательская: пока правка ждёт сети, карточку могли удалить или
переставить с другого клиента. Ни одна операция не имеет права висеть в очереди
вечно, и **пользователь никогда не должен гадать, применилась ли его правка**.

Перед записью очередь перечитывает карточку (`GET /cards/{id}`) — это даёт и
честный `404`, и метку `updated_at` для сравнения. Исходы:

| Исход | Когда | Что делает доска |
|---|---|---|
| `done` | Правка применилась | Тихо, без сообщений |
| `gone` | `404`/`410`: карточку удалили с другого клиента | Правка **инвалидируется**, снимаются **все** операции по этой карточке, карточка убирается с доски. Сообщение: «Карточка #N удалена другим пользователем — ваш перенос отменён» с числом отменённых правок |
| `conflict` | `409`/`412`: сервер отверг из-за расхождения состояния | Повторов нет, доска перезагружается с актуальными данными, пользователь получает объяснение |
| `overwritten` | Применилось, но поверх чужой правки | Сообщение: «Карточку #N параллельно менял кто-то ещё. Применён ваш вариант» |
| `rejected` | Прочие `4xx` (например, `422`) | Откат карточки + текст ошибки от сервера |

### Почему last-write-wins, а не версии

**Это не выбор, а следствие контракта.** В `docs/api-contract.md` нет ни
`version`, ни `ETag`, ни `If-Match` — серверу не с чем сравнивать входящую
запись, поэтому он всегда применяет последнюю. Клиент не может в одностороннем
порядке ввести оптимистичную блокировку: отказаться писать он вправе, но тогда
он просто откажет пользователю там, где сервер бы принял.

Раз запись всё равно побеждает, единственная честная опция — **не молчать об
этом**. Перезапись определяется по `updated_at`: очередь запоминает метку,
которую пользователь видел, когда начал двигать карточку, и сравнивает с той,
что вернул сервер перед нашей записью. Отличается — значит между постановкой в
очередь и отправкой влезла чужая правка, и мы её перекрыли.

Ограничение метода названо честно: метки в контракте **посекундные**, поэтому
чужая правка, пришедшая в ту же секунду, не будет замечена. Надёжное решение —
версионирование на сервере; это задача бэкенда и правка контракта, не фронта.

### Про `409`

Сервер его сегодня **не отдаёт** — отвергать устаревшую запись ему нечем.
Ветка обработки в коде есть и покрыта тестом через мок, чтобы появление
`If-Match` не потребовало переписывать очередь. Это сознательный задел, а не
покрытие ради процента: в тесте прямо указано, что живой сервер этот путь не
вызывает.

## Живое обновление доски

Доска сама подтягивает чужие правки — перезагружать страницу не нужно.

**Опрос раз в 10 секунд.** Почему polling, а не WebSocket: контракт его не
предусматривает, а канбан-доска — не биржевой терминал, задержка в несколько
секунд ничего не стоит. Зато нет второго протокола, переподключений и состояния
на сервере.

Почему именно 10 секунд: чужая правка замечается в пределах обычного разговора
(«переставил — увидел»), нагрузка при этом смешная — один `GET` на вкладку.
Меньше 5 с начинает шуметь во время перетаскивания, больше 20 с — доска
ощущается мёртвой.

Экономим там, где это бесплатно:

- **вкладка скрыта** → опрос останавливается совсем; вернулись → опрос сразу,
  не дожидаясь тика;
- **браузер сообщил `offline`** → попытка не тратится;
- **доска не перерисовывается**, если ничего не изменилось (сравниваются
  видимые поля) — иначе каждые 10 секунд слетал бы фокус и подсветка.

### Что видит пользователь

| Ситуация | Индикатор в шапке |
|---|---|
| Всё в порядке | `обновлено только что` / `12 с назад` |
| Опрос не проходит | `нет связи · данные от 40 с назад` — жёлтая плашка |
| Связь вернулась | Подпись снова спокойная, пауза сбрасывается к 10 с |

**При потере связи доска не пустеет.** Обычная загрузка при ошибке очищает
список — для фонового опроса это недопустимо: данные уже показаны, и мигание
пустой доской из-за одного таймаута хуже, чем слегка устаревшие карточки.
Показываются последние известные данные, честно помеченные несвежими.

Пауза при повторных сбоях растёт: 10с → 20с → 40с → 60с (потолок). Первая
ошибка паузу **не** удлиняет — одиночный таймаут не должен отправлять доску
в долгий сон.

### Очередь главнее опроса

Если по карточке есть неотправленная правка, фоновый опрос **не перезаписывает**
её серверным состоянием. Пользователь уже перетащил карточку; вернуть её назад
означало бы соврать и спровоцировать повторное действие. Остальные карточки при
этом обновляются штатно.

Карточка с локальной правкой, которой уже нет на сервере, тоже остаётся на
доске: её судьбу решает очередь (исход `gone` — см. выше), а не фоновый опрос.
Иначе пользователь увидел бы, как карточка молча исчезла, без объяснения причины.

## Как это работает

- **Drag&drop** — нативный HTML5. Колонка подсвечивается при наведении, перенос
  вызывает `PATCH /cards/{id}` со сменой статуса.
- **Оптимистичный UI**: карточка переезжает сразу, не дожидаясь сервера, —
  дальше по таблице выше.
- **Подтверждение удаления** информативное: если у карточки есть комментарии,
  в предупреждении названо их количество и сказано, что это необратимо. Пустую
  карточку такой текст не сопровождает — рефлекторное «вы уверены?» на всё
  подряд приучает жать «да» не глядя.
- **Ошибки видны**: любая неудача API даёт всплывающее сообщение с кодом и текстом
  (`Не удалось перенести карточку #3 — ошибка 422`). Ошибки не исчезают
  автоматически, успехи гаснут через 3.5 секунды.
- **Валидация на клиенте** дублирует контракт (непустой заголовок ≤ 200 символов),
  чтобы не гонять заведомо плохой запрос, но последнее слово за сервером: `422`
  показывается прямо в форме.
- **Счётчики комментариев** подгружаются фоново и не блокируют отрисовку доски;
  их сбой не тревожит пользователя — это украшение, а не данные.

## Формат ошибок

Расхождение по `422`, найденное при интеграции, **закрыто** (PR #8): бэкенд отдаёт
`detail` строкой, подробности — в необязательном поле `errors`. Формат зафиксирован
в контракте.

Адаптер всё равно поддерживает **оба** формата (строку и массив объектов Pydantic):
это дешёвая страховка на случай, если рядом окажется сервер другой версии.

Мелочь на заметку: `GET /cards?status=` с пустым значением даёт `422` — enum не
принимает пустую строку. Фронт пустой фильтр просто не отправляет, на интерфейсе
это не сказывается.

## Не в этой фазе

Авторизация, websocket, поиск, сортировка внутри колонки, мобильный drag&drop
(на тач-устройствах перенос доступен через диалог: карточка → «Редактировать» →
статус) — кандидаты в спринт 2.
