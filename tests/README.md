# tests/ — контракт-сьют QA

Автотесты соответствия API контракту [`docs/api-contract.md`](../docs/api-contract.md).

## Запуск одной командой

```bash
cd server && python run.py          # в соседнем терминале: сервер на :8000
pip install -r tests/requirements.txt
python -m pytest tests -q           # из корня репозитория
```

Другой адрес: `KANBAN_API=http://host:port/api/v1 python -m pytest tests -q`.
Если сервер не поднят, сьют падает сразу и внятно, а не сотней непонятных ошибок.

Разрушающие тесты на пустой доске по умолчанию пропущены (доска может быть общей):

```bash
KANBAN_ALLOW_WIPE=1 python -m pytest tests -q -m wipe
```

Сквозные тесты полного стенда — отдельно в [`../tests_e2e/`](../tests_e2e/README.md).

## Почему живой HTTP, а не TestClient

Сьют бьёт по `http://localhost:8000` через `httpx`, а не через
`fastapi.TestClient`. Это принципиально: фронтенд ходит по сети, и TestClient
проверяет не то, что увидит фронтенд. Плюс так тесты остаются реализационно
независимыми — их можно гонять против любого корректного сервера.

`server/tests/` (тесты бэкендера) и этот сьют **не дублируют друг друга**:
первые знают про внутренности реализации, вторые — только про контракт.

## Два слоя тестов — не путать

| Слой | Что означает падение |
|---|---|
| обычные тесты | реализация расходится с контрактом → баг зоны `server/` |
| `@pytest.mark.gap` | контракт это место не определяет → нужно решение лида, код не виноват |

Список gap-мест: `python -m pytest tests -q -m gap -v`

## Состояние gap-мест

Из семи найденных неоднозначностей **шесть закрыты**, и все шесть — по находкам
этого сьюта:

| Было gap | Чем закрыто | Где теперь |
|---|---|---|
| коды успеха при создании (`201`) | контракт, 8bf91f6 | строгий слой |
| форма тела `422` (`detail` строкой + `errors`) | PR #8 + 8bf91f6 | строгий слой, 9 ассертов |
| невалидный `?status=` → `422` | арбитраж лида, трактовка 1 | строгий слой |
| `title` из пробелов → `422`, обрезка по краям | арбитраж лида, трактовка 2 | строгий слой |
| `/cards/abc` → `422`, не `404` | арбитраж лида, трактовка 3 | строгий слой |
| пустой текст комментария → `422` | арбитраж лида, трактовка 4 | строгий слой |
| `PATCH {}` → `200` no-op | арбитраж лида, трактовка 5 | строгий слой |
| формат меток без дробной секунды | PR #11 | строгий слой |

**Остался один незакрытый gap** — явный `null` в теле `PATCH`:

```
PATCH {"status": null}      -> 200, карточка не изменилась
PATCH {"priority": null}    -> 200, карточка не изменилась
PATCH {"title": null}       -> 200, карточка не изменилась
PATCH {"description": null} -> 200, карточка не изменилась
```

Контракт требует `422` на невалидный `status`/`priority`, но не говорит,
считается ли `null` невалидным значением или отсутствием поля. Обе трактовки
законны. Предложение формулировки в контракт — в issue #16; пока не принято,
тест фиксирует текущее поведение под маркером `gap`.

## Что ещё покрыто

Параметры списка из спринта 2: `?priority=`, `?limit=` (диапазон `1…200`,
потолок отдаёт `422`, а не обрезание), комбинация фильтров, заголовок
`X-Total-Count` (не зависит от `limit`, зависит от фильтра), пустая выдача как
`200 []`.

## Изоляция

Тесты создают свои карточки и удаляют их в teardown — чужие данные не трогают
и от порядка запуска не зависят. Seed-данные не предполагаются: там, где нужен
конкретный расклад, тест создаёт его сам.

Реестр созданных карточек — отдельная фикстура `created`, а не атрибут на
`httpx.Client`. Teardown не роняет тест из-за уборки, но печатает предупреждение
со списком неуда­лённых id — иначе мусор на доске копился бы незаметно.
