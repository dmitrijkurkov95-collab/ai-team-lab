# tests/ — контракт-сьют QA (задача #4)

Автотесты соответствия API контракту [`docs/api-contract.md`](../docs/api-contract.md).

## Запуск одной командой

```bash
cd server && python run.py          # в соседнем терминале: сервер на :8000
pip install pytest httpx
python -m pytest tests -q           # из корня репозитория
```

Другой адрес: `KANBAN_API=http://host:port/api/v1 python -m pytest tests -q`.
Если сервер не поднят, сьют падает сразу и внятно, а не сотней непонятных ошибок.

Разрушающие тесты на пустой доске по умолчанию пропущены (доска может быть общей):

```bash
KANBAN_ALLOW_WIPE=1 python -m pytest tests -q -m wipe
```

## Почему живой HTTP, а не TestClient

Сьют бьёт по `http://localhost:8000` через `httpx`, а не через
`fastapi.TestClient`. Это принципиально: фронтенд ходит по сети, и TestClient
проверяет не то, что увидит фронтенд. Плюс так тесты остаются реализационно
независимыми — их можно гонять против любого корректного сервера.

`server/tests/` (тесты бэкендера) и этот сьют **не дублируют друг друга**:
первые знают про внутренности реализации, вторые — только про контракт.

## Два слоя тестов — не путать

| Слой | Что означает падение |
|---|---|
| обычные тесты | реализация расходится с контрактом → баг зоны `server/` |
| `@pytest.mark.gap` | контракт это место не определяет → нужно решение лида в `docs/api-contract.md`, код не виноват |

Список gap-мест: `python -m pytest tests -q -m gap -v`

## Найденные расхождения и спорные места

По состоянию на `main` (PR #5 влит). Полный разбор — комментарием в issue #2.

**Расхождений с явными требованиями контракта не найдено.** Все эндпоинты,
коды ошибок, сортировка и форма `404 {"detail": "..."}` — по контракту.

Что требует решения лида (в сьюте помечено `gap`):

1. **Невалидный `?status=`** → `422`. В контракте случай не описан.
2. **`title` из одних пробелов** → `422`, пробелы по краям обрезаются.
   «Непустая строка» не определяет ни того, ни другого.
3. **Не-число в пути** (`/cards/abc`) → `422`, а не `404`.
4. **Пустой текст комментария** → `422`. Контракт описывает тело как `{text}`,
   но про пустое значение молчит.
5. **`PATCH` с пустым телом** → `200` и карточка без изменений.

### Закрыто (было gap, стало строгой проверкой)

- **Формат меток** — расхождение с примером контракта исправлено в PR #11
  (секундная точность + нормализация на границе API). Тест был `xfail`,
  позеленел после фикса и переведён в обычный.
- **Коды успеха** — контракт зафиксировал `POST → 201 (допустим 200)`,
  `GET`/`PATCH` → `200`, `DELETE` → `204`. Проверка переехала в строгий слой.
- **Форма тела `422`** — контракт зафиксировал
  `{"detail": "<строка>", "errors": [...]}` (PR #8). Теперь проверяется строго
  по шести путям в `test_contract.py`, симметрично проверкам `404`.

Пока трактовки не закреплены в контракте, gap-тесты фиксируют текущее поведение:
если оно поедет молча, сьют это покажет. Как только лид допишет контракт —
пометки снимаются и тесты становятся строгими.

## Изоляция

Тесты создают свои карточки и удаляют их в teardown — чужие данные не трогают
и от порядка запуска не зависят. Seed-данные не предполагаются: там, где нужен
конкретный расклад, тест создаёт его сам.
