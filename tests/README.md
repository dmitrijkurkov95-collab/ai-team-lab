# tests/ — контракт-сьют QA

Автотесты соответствия API контракту [`docs/api-contract.md`](../docs/api-contract.md).

## Запуск одной командой

```bash
cd server && python run.py          # в соседнем терминале: сервер на :8000
pip install -r tests/requirements.txt
python -m pytest tests -q           # из корня репозитория
```

Другой адрес: `KANBAN_API=http://host:port/api/v1 python -m pytest tests -q`.
Если сервер не поднят, сьют падает сразу и внятно, а не сотней непонятных ошибок.

Разрушающие тесты на пустой доске по умолчанию пропущены (доска может быть общей):

```bash
KANBAN_ALLOW_WIPE=1 python -m pytest tests -q -m wipe
```

Сквозные тесты полного стенда — отдельно в [`../tests_e2e/`](../tests_e2e/README.md).

## Почему живой HTTP, а не TestClient

Сьют бьёт по `http://localhost:8000` через `httpx`, а не через
`fastapi.TestClient`. Это принципиально: фронтенд ходит по сети, и TestClient
проверяет не то, что увидит фронтенд. Плюс так тесты остаются реализационно
независимыми — их можно гонять против любого корректного сервера.

`server/tests/` (тесты бэкендера) и этот сьют **не дублируют друг друга**:
первые знают про внутренности реализации, вторые — только про контракт.

## Два слоя тестов — не путать

| Слой | Что означает падение |
|---|---|
| обычные тесты | реализация расходится с контрактом → баг зоны `server/` |
| `@pytest.mark.gap` | контракт это место не определяет → нужно решение лида, код не виноват |

Список gap-мест: `python -m pytest tests -q -m gap -v`

## Состояние gap-мест

Из семи найденных неоднозначностей **шесть закрыты**, и все шесть — по находкам
этого сьюта:

| Было gap | Чем закрыто | Где теперь |
|---|---|---|
| коды успеха при создании (`201`) | контракт, 8bf91f6 | строгий слой |
| форма тела `422` (`detail` строкой + `errors`) | PR #8 + 8bf91f6 | строгий слой, 9 ассертов |
| невалидный `?status=` → `422` | арбитраж лида, трактовка 1 | строгий слой |
| `title` из пробелов → `422`, обрезка по краям | арбитраж лида, трактовка 2 | строгий слой |
| `/cards/abc` → `422`, не `404` | арбитраж лида, трактовка 3 | строгий слой |
| пустой текст комментария → `422` | арбитраж лида, трактовка 4 | строгий слой |
| `PATCH {}` → `200` no-op | арбитраж лида, трактовка 5 | строгий слой |
| формат меток без дробной секунды | PR #11 | строгий слой |

**Остался один незакрытый gap** — явный `null` в теле `PATCH`:

```
PATCH {"status": null}      -> 200, карточка не изменилась
PATCH {"priority": null}    -> 200, карточка не изменилась
PATCH {"title": null}       -> 200, карточка не изменилась
PATCH {"description": null} -> 200, карточка не изменилась
```

Контракт требует `422` на невалидный `status`/`priority`, но не говорит,
считается ли `null` невалидным значением или отсутствием поля. Обе трактовки
законны. Предложение формулировки в контракт — в issue #16; пока не принято,
тест фиксирует текущее поведение под маркером `gap`.

## Два новых gap-места (#29, спринт 3)

Найдены при закрытии дыр покрытия. Оба помечены `gap` — это вопросы к лиду, а
не приговор реализации:

**1. Дубликаты `id` в файле проверяются только в `mode=replace`.**
Контракт говорит «дубликаты `id` внутри одного файла → `422`» без оговорки про
режим, но в коде проверка стоит внутри ветки `replace`, и `merge` отвечает
`200`. Практического ущерба нет — в `merge` id из файла всё равно отбрасываются,
коллизии в базе не будет. Но клиент получает разный ответ на один и тот же
кривой файл в зависимости от режима.
_Решение: сузить формулировку контракта до `replace` либо поднять проверку выше
ветвления._

**2. `422` из `HTTPException` приходит без поля `errors`.**
Контракт задаёт форму `{"detail": "...", "errors": [...]}` для кода `422`
целиком, но `errors` добавляет только обработчик `RequestValidationError`.
Ручные отказы (те же дубликаты `id`) отдают голый `detail`. Это тот же класс
проблемы, что чинили в PR #8, только наоборот: тогда `detail` был массивом у
всех, теперь `errors` отсутствует у части ответов.
_Решение: дописать `errors` в ручные отказы (или общий обработчик
`HTTPException`) либо смягчить формулировку до «ошибок валидации тела»._

## Что ещё покрыто

**Спринт 2:** `?priority=`, `?limit=` (диапазон `1…200`, потолок отдаёт `422`, а
не обрезание), комбинация фильтров, заголовок `X-Total-Count` (не зависит от
`limit`, зависит от фильтра), пустая выдача как `200 []`.

**Спринт 3** — `test_list_params.py` и `test_export_import.py`, закрывают дыру
из аудита #29 (эти фичи проверялись только unit-тестами автора реализации):

| Область | Ключевое из проверяемого |
|---|---|
| Поиск `?q=` | подстрока в `title` **или** `description`, регистронезависимость **кириллицы**, `%` и `_` буквально, обрезка пробелов, пустой запрос → `422`, потолок 200 символов |
| Пагинация `?offset=` | страницы не пересекаются, `offset=0` ≡ без параметра, за пределами выборки → `200 []` (не `404`), отсутствие потолка, `X-Total-Count` не зависит от `offset` |
| Сортировка `?sort=`/`?order=` | `priority` по смыслу (`high > normal > low`, не по алфавиту), тай-брейк по `id`, дефолт `id ASC`, белый список значений |
| Дедлайны | приведение к UTC (со смещением и без), прошлое разрешено, `null` снимает срок, непереданное поле сохраняет, пустой срок всегда в конце, отсутствие `is_overdue` |
| Экспорт | обязательные поля, вложенные комментарии, не файл (без `Content-Disposition`) |
| Импорт | `mode` обязателен, `format_version` и `cards` обязательны, `cards` массивом, атомарность, валидация как у `POST /cards`, `merge` выдаёт новые id |
| Защита #54/#57 | `428` без подтверждения и точное сравнение значения, `413` на потолках (10 000 карточек / 2 MB), `merge` без подтверждения работает, round-trip, продолжение счётчика id |
| Токен записи | класс `TestЗащитаЗаписи` — пропускается, если `KANBAN_WRITE_TOKEN` не задан; проверяет `401`, открытое чтение и независимость токена от подтверждения |
| `/health` | помечен `gap`: ручки нет в контракте, но на неё завязаны `run.sh`, healthcheck и CI |

Разрушающие проверки импорта (`replace`, очистка доски) помечены `wipe` и
восстанавливают доску через фикстуру `restore_board` даже при падении.

## Изоляция

Тесты создают свои карточки и удаляют их в teardown — чужие данные не трогают
и от порядка запуска не зависят. Seed-данные не предполагаются: там, где нужен
конкретный расклад, тест создаёт его сам.

Реестр созданных карточек — отдельная фикстура `created`, а не атрибут на
`httpx.Client`. Teardown не роняет тест из-за уборки, но печатает предупреждение
со списком неуда­лённых id — иначе мусор на доске копился бы незаметно.
