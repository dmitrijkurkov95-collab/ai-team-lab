# Контракт API канбан-доски

Base URL: `http://localhost:8000/api/v1`
Формат: JSON везде.

## Коды и формат ошибок

- Успех: `GET`/`PATCH` → `200`, `POST` → `201` (допустим `200`), `DELETE` → `204`
- `404` → `{"detail": "<строка>"}`
- `422` → `{"detail": "<строка для человека>", "errors": [<подробности для отладки>]}` — клиенту достаточно `detail`, поле `errors` можно игнорировать

_Зафиксировано по итогам PR #8: ранее формат 422 был неоднозначным, из-за чего клиенту приходилось разбирать два разных формата._

## Сущность Card

```json
{
  "id": 42,
  "title": "Сделать дизайн колонок",
  "description": "optional, may be empty",
  "status": "backlog",
  "priority": "normal",
  "created_at": "2026-08-26T12:00:00Z",
  "updated_at": "2026-08-26T12:30:00Z",
  "deadline": "2026-09-01T18:00:00Z"
}
```

- `status`: `backlog` | `in_progress` | `review` | `done`
- `priority`: `low` | `normal` | `high`
- `title`: непустая строка до 200 символов
- `deadline`: срок в формате меток контракта или `null` — срок есть не у каждой задачи

## Эндпоинты

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/cards` | список; опциональные `?status=`, `?priority=`, `?limit=`, `?offset=`, `?q=`, `?sort=`, `?order=` — см. «Параметры списка» |
| POST | `/cards` | создать; тело: `{title, description?, priority?, deadline?}` (defaults: empty, `normal`, `null`) |
| GET | `/cards/{id}` | одна карточка |
| PATCH | `/cards/{id}` | частичное обновление любых полей; смена `status` = перемещение по доске |
| DELETE | `/cards/{id}` | удалить, `204` |
| POST | `/cards/{id}/comments` | добавить комментарий `{text}` |
| GET | `/cards/{id}/comments` | список комментариев к карточке |

## Параметры списка `GET /cards`

Все параметры опциональны и комбинируются: `?status=done&priority=high&limit=10&offset=20&q=дизайн`.

| Параметр | Значения | По умолчанию | Поведение |
|---|---|---|---|
| `status` | `backlog` \| `in_progress` \| `review` \| `done` | без фильтра | только карточки этой колонки |
| `priority` | `low` \| `normal` \| `high` | без фильтра | только карточки этого приоритета |
| `limit` | целое `1…200` | без ограничения | не больше N карточек, первые по возрастанию `id` |
| `offset` | целое `≥ 0` | `0` | пропустить первые N карточек выборки |
| `q` | непустая строка до 200 символов | без поиска | подстрока в `title` **или** `description`, без учёта регистра |
| `sort` | `created` \| `priority` \| `deadline` | `id` по возрастанию | поле сортировки |
| `order` | `asc` \| `desc` | `asc` | направление сортировки |

Неочевидные случаи — определены явно, чтобы не додумывать:

- `status` или `priority` вне списка допустимых → `422`
- `limit=0`, отрицательный, не число, пустой (`?limit=`) → `422`
- `limit` больше потолка `200` → `422` (не молчаливое обрезание: иначе клиент считает выдачу полной, а она урезана)
- фильтр ничего не нашёл → `200` и пустой массив `[]` — это не ошибка

**Дефолтного лимита нет: без параметра возвращаются все карточки.** Доска рисует колонки целиком, и молчаливое обрезание означало бы неполный интерфейс без предупреждения — тот же изъян, из-за которого `limit>200` отдаёт `422`, а не урезанный список. Потолок `200` применяется только к явному `?limit=`.

Ответ `GET /cards` содержит заголовок **`X-Total-Count`** — сколько карточек попадает под фильтр без учёта `limit` **и `offset`**. По нему клиент видит, что выдача урезана, и считает число страниц, не угадывая.

### Постраничная навигация (`offset`)

Страница — это `?limit=N&offset=K`: `limit` задаёт размер, `offset` — сдвиг от начала выборки. Схема выбрана offset-based, а не курсорная — обоснование в PR к #27, кратко: сортировка фиксирована (`id ASC`), клиенту нужны прыжки на произвольную страницу и счётчик страниц из `X-Total-Count`, а курсор это как раз запрещает.

Неочевидные случаи — определены явно:

- `offset` отрицательный, не целое, пустой (`?offset=`) → `422`
- `offset` за пределами выборки → `200` и пустой массив `[]`. Не `404`: хвост, из которого карточки успели удалить, — не ошибка клиента
- `offset=0` эквивалентен запросу без параметра
- `offset` без `limit` → все карточки, начиная с N-й
- **у `offset` нет потолка**, в отличие от `limit`. Потолок `limit` защищает размер ответа; большой `offset` ответ не раздувает, ограничивать нечего
- `X-Total-Count` от `offset` не зависит — это размер выборки под фильтром, якорь для расчёта страниц

**Известная слабость offset (сознательная):** список меняется между запросами → границы страниц едут. Удалили карточку из уже показанной страницы — одна карточка на стыке будет пропущена; добавили в середину — одна повторится. Для доски с ручным редактированием это приемлемо: правки редки, а `X-Total-Count` даёт клиенту заметить расхождение. Понадобится строгая гарантия «каждый элемент ровно один раз» (бесконечный скролл, экспорт) — заводим Issue на курсор `?after=<id>`, он ложится на ту же сортировку по `id` без слома контракта.

### Дедлайны и сортировка

**`deadline`** — nullable, тот же формат меток, что `created_at`/`updated_at`. Принимается ISO 8601 со смещением (`2026-09-01T21:00:00+03:00`) и без зоны — приводится к UTC, чтобы в базе лежал один формат и сортировка по строке совпадала с хронологией. Без зоны трактуется как UTC: молчаливый сдвиг на зону сервера увёл бы срок на часы незаметно для пользователя.

- **Дедлайн в прошлом разрешён.** Запрет сломал бы импорт исторических досок и правку задним числом, а просроченная задача — нормальное состояние, а не ошибка ввода
- невалидная дата, пустая строка, не-строка → `422`
- `PATCH {"deadline": null}` — **снять срок**; это осмысленный запрос и он отличается от «поле не передано» (тогда срок сохраняется)
- **Просрочку вычисляет клиент, а не сервер.** Сервер отдаёт факт (`deadline`), а не мнение (`is_overdue`): вычисленный флаг протухает в ту же секунду, что и ответ, а «что считать концом дня» и часовой пояс пользователя — вопрос интерфейса

**Сортировка `?sort=` + `?order=`:**

- `created` — по `created_at`; `priority` — **по смыслу `high > normal > low`**, не по алфавиту; `deadline` — по сроку
- значение вне списка → `422` (белый список: имя поля из запроса не доезжает до SQL)
- **дефолт — `id ASC`**, ровно как до появления параметра: доска, не знающая про сортировку, работает как раньше
- **тай-брейк по `id` всегда**, в ту же сторону, что и основной ключ. Метки округлены до секунды, поэтому у пачки карточек ключ совпадает; без тай-брейка страницы пагинации поехали бы (урок #11/#27), а с жёстким `id ASC` запрос «сначала новые» показывал бы внутри пачки сначала старые
- **карточки без `deadline` — всегда в конце**, независимо от `order`. «Срока нет» — это не «срок бесконечно ранний»: пустой хвост в начале списка выглядел бы как баг

### Поиск `?q=`

Поиск подстроки одновременно по `title` и `description` (условие «или»), без учёта регистра — **включая кириллицу**.

Неочевидные случаи — определены явно:

- `?q=` без значения, пустая строка, одни пробелы/табы → `422`. Не «фильтр, который молча не фильтрует»: клиент должен знать, что запрос бессмысленный, а не получать всю доску под видом результата поиска
- пробелы по краям обрезаются: `?q= дизайн ` и `?q=дизайн` — один запрос
- `q` длиннее 200 символов → `422` (столько же, сколько максимальный `title`)
- ничего не нашлось → `200` и пустой массив `[]`
- **символы `%` и `_` ищутся буквально**, а не как маски LIKE: поиск по `100%` находит карточки со «100%», а не всё подряд
- поиск — это подстрока, не префикс: «колонк» найдёт «Сверстать колонки». Морфологии и опечаток нет, это точное вхождение
- `X-Total-Count` учитывает `q` так же, как остальные фильтры

_Регистронезависимость кириллицы отдельно оговорена, потому что встроенный `LIKE` в SQLite приводит регистр только для ASCII: «Карточка» по запросу «карточка» без доработки не находилась бы._

## Правила поведения

- `PATCH` с невалидным `status`/`priority` → `422`
- `POST /cards` с пустым `title` или >200 символов → `422`
- Списки возвращают массивы по возрастанию `id`; комментарии — по времени создания
- Часовые метки — ISO 8601 UTC

Контракт может расширяться (спринт 2+: поиск, теги, дедлайны) — изменения только через PR в этот файл с апрувом лида.

## Трактовки неоднозначных случаев

_Арбитраж лида по gap-находкам QA (PR #13). Реализация обязана соблюдать все пять пунктов._

1. Невалидный `?status=` в фильтре → `422` (не пустой список и не 500)
2. `title` из одних пробелов → `422`; валидный `title` обрезается по краям
3. Не-числовой `id` в пути (`/cards/abc`) → `422`, а не `404`
4. Пустой текст комментария → `422`
5. `PATCH` с пустым телом → `200`, карточка без изменений (идемпотентность)
